## 7.1 プラットフォーム候補の比較

| 観点 | Webアプリ（PWA） | ネイティブモバイル | クロスプラットフォーム（React Native / Flutter） |
|------|------------------|--------------------|------------------------------------------------|
| 開発速度・初期コスト | ◎ 速い・低コスト | △ OSごとに開発 | ○ 1コードで2OS |
| インストール不要 | ◎ URLで即利用 | × ストア経由 | × ストア経由 |
| オフライン学習 | ○ Service Worker | ◎ 得意 | ◎ 得意 |
| プッシュ通知 | △ 制約あり（特にiOS） | ◎ | ◎ |
| 音声録音/STT（発音練習） | ○ Web API（精度/対応に差） | ◎ ネイティブAPI | ○ プラグイン |
| 配布・更新の容易さ | ◎ 即時反映 | △ 審査 | △ 審査 |
| スキマ学習との相性 | ○ | ◎ 端末に常駐 | ◎ |

### 推奨の考え方
- **MVPを素早く検証**したいなら **Web（PWA）** が有力。インストール障壁が低く、更新も容易。
- **通知による習慣化・発音練習・オフライン**を重視するなら **モバイル**（クロスプラットフォーム）が有利。
- 折衷案: **PWA でMVP → 反応を見てモバイル化**、もしくは最初から **Flutter/React Native** で両取り。

> 決定に必要な追加インプット（`要検討`）: 主要ターゲットの利用端末、通知/発音練習の優先度、開発リソース。

## 7.2 アーキテクチャ案（プラットフォーム非依存）

```
[クライアント (Web/モバイル)]
   - 学習UI / 演習ロジック / SRSスケジューラ（クライアント側計算も可）
   - ローカルDB（オフライン: IndexedDB / SQLite 等）
        │  REST or GraphQL（HTTPS）
        ▼
[バックエンドAPI]
   - 認証 / 同期 / コンテンツ配信 / 統計集計
        │
        ▼
[データストア]  +  [オブジェクトストレージ（音声アセット）]
        +
[外部サービス]  TTS / STT / 翻訳 / AI採点（必要に応じて）
```

- **SRS計算をどこで行うか**は設計判断（`要検討`）。
  - クライアント計算＋サーバ同期（オフライン強い） / サーバ計算（一貫性強い）。

## 7.3 技術スタック候補（たたき台）

> いずれも案。確定ではない（`要検討`）。

| レイヤ | 候補 |
|--------|------|
| フロント（Web） | React / Next.js, TypeScript, PWA |
| フロント（モバイル） | Flutter もしくは React Native |
| 状態/ローカルDB | IndexedDB（Web）/ SQLite（モバイル） |
| バックエンド | Node.js(NestJS) / Python(FastAPI) など。または BaaS（Supabase / Firebase） |
| データベース | PostgreSQL（リレーショナル、SRS/集計に好相性） |
| 認証 | BaaS内蔵 or 自前（メール/ソーシャル） |
| 音声(TTS) | クラウドTTS（高品質）or 端末内蔵TTS（低コスト） |
| 発音評価(STT) | クラウドSTT or 端末API（採用は発音機能の優先度次第） |
| インフラ | マネージド（Vercel / Cloud Run / Fly.io 等） |
| 監視 | Sentry 等 |

### BaaS（Supabase/Firebase）採用の論点
- 利点: 認証・DB・同期・ストレージが揃い、**MVPを高速に**作れる。
- 注意: ベンダーロックイン、複雑なSRSクエリ/集計の柔軟性。

## 7.4 外部依存とコスト
- TTS/STT/翻訳/AI採点 は**従量課金**。利用箇所と量を見積もり、キャッシュ（生成音声の再利用）で最適化する。
- 例文コンテンツの調達方法（自作 / オープンライセンス / 生成AI）でコストと権利が変わる（[04](04-非機能要件.md) 4.9）。
