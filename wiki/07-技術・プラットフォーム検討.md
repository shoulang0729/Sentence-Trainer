# 07. 技術・プラットフォーム検討

> **プラットフォーム: Web（PWA）で開始（決定）。将来モバイル化を検討。**
>
> 前提: **個人用だが共有/学習状況シェアがある**ため、アカウントとバックエンド（同期）は必須。

## 7.1 プラットフォーム候補の比較

| 観点 | Webアプリ（PWA）★採用 | ネイティブモバイル | クロスプラットフォーム（React Native / Flutter） |
|------|------------------|--------------------|------------------------------------------------|
| 開発速度・初期コスト | ◎ 速い・低コスト | △ OSごとに開発 | ○ 1コードで2OS |
| インストール不要 | ◎ URLで即利用 | × ストア経由 | × ストア経由 |
| 中国語入力（IME） | ◎ OS標準IME利用 | ◎ | ◎ |
| 一括登録（ファイル/貼付） | ◎ デスクトップ併用が快適 | △ モバイルは貼付中心 | △ |
| オフライン学習 | ○ Service Worker | ◎ | ◎ |
| プッシュ通知 | △ 制約あり（特にiOS） | ◎ | ◎ |
| 発音録音/STT | ○ Web API（精度差） | ◎ ネイティブAPI | ○ プラグイン |
| 配布・更新 | ◎ 即時反映 | △ 審査 | △ 審査 |

### 決定: Web（PWA）でMVP → 将来モバイル化を検討

**採用理由:**
- **「作るのはPC・覚えるのはスマホ」を1つでカバー**できるのはWebだけ。一括登録（CSV）はPCブラウザが快適、トレーニングはスマホのブラウザ/PWAで可能。
- **MVPを最速・最小コストで検証**できる（方針「なるべく削る」に合致）。
- **Supabaseとの相性が良い**（Web向けSDKが充実）。
- Webの弱点である**通知（Phase2）・発音録音（Phase4）はいずれも後続フェーズ**のため、当面は影響しない。

**将来:** 本格的な習慣化通知や発音が必要になった段階で、**Flutter / React Native でモバイル化**を検討。バックエンド（Supabase）は共通で使い回せるため移行コストは小さい。

> 弱点の通知が「続ける肝」になるなら最初からモバイルも選択肢だが、本プロジェクトは通知をPhase2送りと判断済みのため Web（PWA）を採用。

## 7.2 アーキテクチャ案

```
[クライアント (Web / PWA)]
   - 登録UI / トレーニングUI（2モード・トグル表示） / SRSスケジューラ(SM-2)
   - ローカルDB（オフライン: IndexedDB）
        │  Supabase Client SDK（HTTPS / REST）
        ▼
[Supabase]
   - Auth（認証） / PostgreSQL（保存・同期・統計集計） / Storage（音声アセット）
   - Row Level Security（共有・グループの権限制御） / Edge Functions（外部API呼び出し・鍵秘匿）
        │
        ▼
[外部サービス]  中国系LLM/API（ピンイン生成・TTS）/ STT（発音評価, 後続）
```

- **SRS計算はクライアント側で実施**（SM-2でCardの状態を更新し、Supabaseに保存・同期）。Supabaseは保存と同期に徹する。
- **ピンイン生成・音声(TTS)**: 中国系LLM/APIで生成し、結果をキャッシュ（詳細は §7.4）。Edge Functions経由で呼び出し、APIキーを秘匿。
- 将来モバイル化する場合、ローカルDBは SQLite 等に置き換え（バックエンドは共通）。

## 7.3 技術スタック候補（たたき台）

> いずれも案。確定ではない（`要検討`）。

| レイヤ | 候補 |
|--------|------|
| フロント | **Web（PWA）（決定）**: React / Next.js, TypeScript |
| フロント（将来モバイル） | Flutter もしくは React Native（後続で検討） |
| 状態/ローカルDB | IndexedDB（Web。オフライン学習用） |
| バックエンド | **Supabase（決定）** — クラウド版で開始、必要に応じてセルフホストへ |
| データベース | **PostgreSQL**（Supabase内蔵。リレーショナル、共有・統計に好相性） |
| 認証 | **Supabase Auth**（メール/パスワード、ソーシャル。匿名→後リンクも） |
| 音声(TTS) | **中国系LLM/API（アリババ系等）で生成（決定）** ＋ 結果をキャッシュ |
| ピンイン変換 | **中国系LLM/API（アリババ系等）で生成（決定）**。フォールバックにライブラリ |
| 発音評価(STT) | クラウドSTT（後続フェーズ、声調評価は `要検討`） |
| インフラ | マネージド（Vercel / Cloud Run / Fly.io 等） |
| 監視 | Sentry 等 |

### バックエンド: Supabase（決定）

オープンソースのBaaS。中身は実績ある部品（PostgreSQL / GoTrue認証 / PostgREST API / Storage）の統合。

**採用理由:**
- **共有・グループのアクセス制御**を PostgreSQL の **Row Level Security（行レベルセキュリティ）** で素直に書ける（Phase 3の肝）。
- **統計の集計**（登録数・自己評価良好割合・日別量）が SQL（GROUP BY等）で自在 → 「記録を残したい」要望に直結。
- 既存の[データモデル](06-データモデル.md)（Sentence/Card/ReviewLog のリレーショナル設計）がそのまま乗る。
- 認証・ストレージ（TTS音声）・自動APIも込みで **MVPを最速で立ち上げ**られる。
- **オープンソース**のためロックインが弱い：クラウド版で開始し、将来セルフホストや他PostgreSQLへ移行可能。

**運用方針:** まず **Supabaseクラウド版**（無料枠→規模で課金）で開始。必要になれば **セルフホスト**へ移行。

**留意点:**
- 凝ったサーバ側ロジックが必要になれば Edge Functions（サーバレス関数）で補う。
- 無料枠の制限（一定期間アクセスがないと一時停止等）はβ段階で要確認（`要検討`）。

> 比較検討した代替: Firebase（集計・行権限が要件に不利）、Appwrite / PocketBase（小規模向き・実績/集計でSupabaseに劣る）。本アプリは「共有の権限制御＋集計＋リレーショナル」が肝のため Supabase を選定。

## 7.4 外部依存とコスト

### ピンイン生成・TTS: 中国系LLM/API（決定）
- **ピンイン変換・音声読み上げ（TTS）は、アリババ系など中国系のLLM/APIで生成**する。
  - 中国語に最適化されており、声調・自然な発音・多音字の文脈判定で有利。
  - 候補例（`要検討`）: Alibaba Cloud（Qwen系LLM / 通義系の音声合成）等。具体プロバイダ・モデルは選定時に確定。
- **生成タイミング**: センテンス登録時（個別/一括）に生成し、結果を**Supabase（DB＝ピンイン、Storage＝音声ファイル）にキャッシュ**。再生時は再生成しない。
- **コスト最適化**: 同一テキストは再利用。一括登録時はまとめて生成。
- **留意点（`要検討`）**:
  - APIキーはサーバ側（Supabase Edge Functions等）で秘匿し、クライアントに出さない。
  - 中国リージョンAPI利用時のネットワーク到達性・レイテンシ・利用規約を確認。
  - フォールバック: API不調時はピンインをライブラリ（pypinyin 等）で暫定生成も可。

### その他
- 発音の自動評価（声調含む）は精度・コストの難度が高いため、**自己評価/録音聞き返しから開始**し、段階導入（[08](08-ロードマップとMVP.md)）。
