# 07. 技術・プラットフォーム検討

> プラットフォームは**未確定**。本ページで選択肢を比較し、意思決定の材料を整理する。最終決定は別途記録する（`TBD`）。

## 7.1 プラットフォーム候補の比較

| 観点 | Webアプリ（PWA） | ネイティブモバイル | クロスプラットフォーム（React Native / Flutter） |
|------|------------------|--------------------|------------------------------------------------|
| 開発速度・初期コスト | ◎ 速い・低コスト | △ OSごとに開発 | ○ 1コードで2OS |
| インストール不要 | ◎ URLで即利用 | × ストア経由 | × ストア経由 |
| 中国語入力（IME） | ◎ OS標準IME利用 | ◎ | ◎ |
| 一括登録（ファイル/貼付） | ◎ デスクトップ併用が快適 | △ モバイルは貼付中心 | △ |
| オフライン学習 | ○ Service Worker | ◎ | ◎ |
| プッシュ通知 | △ 制約あり（特にiOS） | ◎ | ◎ |
| 発音録音/STT | ○ Web API（精度差） | ◎ ネイティブAPI | ○ プラグイン |
| 配布・更新 | ◎ 即時反映 | △ 審査 | △ 審査 |

### 推奨の考え方
- **一括登録やセンテンス管理はPC（Web）が快適**、一方で**日々の復習・通知はモバイルが有利**。
- 折衷案: **Web（PWA）でMVP** → 反応を見てモバイル化、または最初から**クロスプラットフォーム**で両取り。
- 共有がある以上、いずれの場合も**バックエンド＋同期**が前提。

> 決定に必要な追加インプット（`要検討`）: 主に使う端末（PC中心/スマホ中心）、通知・発音の優先度、開発リソース。

## 7.2 アーキテクチャ案（プラットフォーム非依存）

```
[クライアント (Web/モバイル)]
   - 登録UI / トレーニングUI（2モード・トグル表示） / SRSスケジューラ(SM-2)
   - ローカルDB（オフライン: IndexedDB / SQLite 等）
        │  Supabase Client SDK（HTTPS / REST）
        ▼
[Supabase]
   - Auth（認証） / PostgreSQL（保存・同期・統計集計） / Storage（音声アセット）
   - Row Level Security（共有・グループの権限制御） / Edge Functions（必要時）
        │
        ▼
[外部サービス]  TTS（音声生成）/ ピンイン変換 / STT（発音評価, 後続）
```

- **SRS計算はクライアント側で実施**（SM-2でCardの状態を更新し、Supabaseに保存・同期）。Supabaseは保存と同期に徹する。
- **ピンイン自動生成**: ライブラリ（例: pypinyin 等）or API（`要検討`）。
- **音声(TTS)**: 中国語対応TTSで生成し、結果をキャッシュ（コスト最適化）。

## 7.3 技術スタック候補（たたき台）

> いずれも案。確定ではない（`要検討`）。

| レイヤ | 候補 |
|--------|------|
| フロント（Web） | React / Next.js, TypeScript, PWA |
| フロント（モバイル） | Flutter もしくは React Native |
| 状態/ローカルDB | IndexedDB（Web）/ SQLite（モバイル） |
| バックエンド | **Supabase（決定）** — クラウド版で開始、必要に応じてセルフホストへ |
| データベース | **PostgreSQL**（Supabase内蔵。リレーショナル、共有・統計に好相性） |
| 認証 | **Supabase Auth**（メール/パスワード、ソーシャル。匿名→後リンクも） |
| 音声(TTS) | 中国語対応クラウドTTS（生成＋キャッシュ） |
| ピンイン変換 | ライブラリ or API |
| 発音評価(STT) | クラウドSTT（後続フェーズ、声調評価は `要検討`） |
| インフラ | マネージド（Vercel / Cloud Run / Fly.io 等） |
| 監視 | Sentry 等 |

### バックエンド: Supabase（決定）

オープンソースのBaaS。中身は実績ある部品（PostgreSQL / GoTrue認証 / PostgREST API / Storage）の統合。

**採用理由:**
- **共有・グループのアクセス制御**を PostgreSQL の **Row Level Security（行レベルセキュリティ）** で素直に書ける（Phase 3の肝）。
- **統計の集計**（登録数・正答率・日別量）が SQL（GROUP BY等）で自在 → 「記録を残したい」要望に直結。
- 既存の[データモデル](06-データモデル.md)（Sentence/Card/ReviewLog のリレーショナル設計）がそのまま乗る。
- 認証・ストレージ（TTS音声）・自動APIも込みで **MVPを最速で立ち上げ**られる。
- **オープンソース**のためロックインが弱い：クラウド版で開始し、将来セルフホストや他PostgreSQLへ移行可能。

**運用方針:** まず **Supabaseクラウド版**（無料枠→規模で課金）で開始。必要になれば **セルフホスト**へ移行。

**留意点:**
- 凝ったサーバ側ロジックが必要になれば Edge Functions（サーバレス関数）で補う。
- 無料枠の制限（一定期間アクセスがないと一時停止等）はβ段階で要確認（`要検討`）。

> 比較検討した代替: Firebase（集計・行権限が要件に不利）、Appwrite / PocketBase（小規模向き・実績/集計でSupabaseに劣る）。本アプリは「共有の権限制御＋集計＋リレーショナル」が肝のため Supabase を選定。

## 7.4 外部依存とコスト
- TTS / STT / ピンイン変換 は従量課金になりうる。**生成結果のキャッシュ**で最適化。
- 発音の自動評価（声調含む）は精度・コストの難度が高いため、**自己評価/録音聞き返しから開始**し、段階導入（[08](08-ロードマップとMVP.md)）。
